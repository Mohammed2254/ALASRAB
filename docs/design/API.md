# واجهة الـAPI (Stage 3)

> **القاعدة:** كل endpoint يقابل متطلَّبًا، وكل متطلَّب له endpoint. الفجوات تُعلَن.
> **التوليد:** `flask-smorest` يولّد OpenAPI من `schemas/` — **العقد من الكود لا
> بجانبه**، فلا يفترقان بعد شهر.

---

## ١. قواعد عامّة

| | |
|---|---|
| الجذر | `/api` |
| الترميز | JSON · UTF-8 |
| المصادقة | كوكي جلسة `HttpOnly` — **لا ترويسة `Authorization`** |
| التواريخ | ISO-8601 بـUTC في النقل · **العرض بتوقيت المنظمة في الواجهة** |
| الأرقام | نصّ عشري للمبالغ (`"12.50"`) — **لا `float`** فلا يفقد الدقّة في JS |
| الترقيم | `?limit&cursor` حيث تكبر القائمة |

**كل طلب غير `GET`/`HEAD`** يمرّ بفحص `Origin` — **وغيابها رفضٌ لا تساهل**
(`403`). طبقة ثانية فوق `SameSite=Lax` (ADR-006).

**حدود المعدّل:** `/auth/login` ٥/١٥د · `/notes` ١٠/ساعة · `/me/readings` ٢٠/يوم.
تجاوزها `429` **يذكر متى يُفتح**.

**كل ردّ خطأ بالشكل نفسه:**
```json
{ "message": "الرسالة التي يقرأها المستخدم", "errors": { "field": ["..."] } }
```
**حتى غير المتوقَّع منه:** معالج في `create_app` يلتقط أي استثناء غير ملتقَط،
**يسجّل التفصيل ولا يرسله**، ويردّ `500` بنفس الشكل. بلاه يردّ Flask صفحة HTML
فيكسر العقد، ويعرض أثر التنفيذ في وضع التنقيح.

### الحرّاس
| الحارس | يفرض |
|---|---|
| `@login_required` | جلسة سارية غير مُبطَلة |
| `@admin_required` | العضوية الحالية `role='admin'` |
| **نطاق كل استعلام إداري** | **`org_id` وحده.** المشرف على مستوى الجمعية — `team_id` مرشّح واجهة **لا حاجز أمني** (`ARCHITECTURE.md` §٧.٣) |

## ٢. مسارات بنيوية — بلا متطلَّب وظيفي

| المسار | الطريقة | الغرض البنيوي | الحارس |
|---|---|---|---|
| `/health` | GET | **يفحص اتّصال القاعدة فعلًا** لا يردّ `200` أعمى | — |
| `/openapi.json` · `/docs` | GET | العقد المولَّد من `schemas/` | **معطَّل افتراضيًّا** — يُفعَّل بـ`EXPOSE_API_DOCS` |

**لماذا لا متطلَّب لها؟** لأنها تخدم **التشغيل لا المستخدم**: منصّة الاستضافة
تحتاج نقطة فحص، والمطوّر يحتاج العقد. **وهذا استثناء معلَن لا فجوة تتبّع** —
البوابة تشترط «متطلَّب **أو** غرض بنيوي موثَّق».

> `/health` يفحص القاعدة لأن خادمًا يردّ `200` وقاعدته ساقطة **يخدع المراقبة
> ويؤخّر اكتشاف العطل**.

## ٣. المصادقة

| المسار | الطريقة | الغرض | FR | الحارس |
|---|---|---|---|---|
| `/auth/login` | POST | دخول بـ`student_no` + PIN · قفل بعد ٥ محاولات | FR-001 · FR-003 | — |
| `/auth/logout` | POST | إبطال الجلسة **في القاعدة** | FR-002 | `login` |
| `/auth/me` | GET | المستخدم الحالي ودوره | FR-002 | `login` |

**`POST /auth/login`**
```json
→ { "student_no": "1042", "pin": "8317" }
← 200 { "user": { "id": 7, "full_name": "...", "role": "pilot" } }
```
| خطأ | الرمز | الرسالة |
|---|--:|---|
| بيانات خاطئة | 401 | **«رقم الطالب أو الرمز غير صحيح»** — رسالة **واحدة** للحالتين |
| حقل مجهول (مثل `org_id`) | 422 | يُرفض صاخبًا لا يُتجاهل صامتًا |
| قفل | 429 | «حاولت ٥ مرات. جرّب بعد ١٥ دقيقة.» — **يذكر متى** |

> 🔒 التفريق بين «رقم غير موجود» و«رمز خاطئ» يحوّل الشاشة إلى **أداة تعداد
> للطلاب**. الرسالة الواحدة ليست غموضًا بل ضمانة.
>
> **والزمن جزء من الرسالة.** بلا تهشير وهمي حين لا يوجد المستخدم، يردّ الرقم
> المجهول فورًا ويدفع الموجودُ كلفة argon2id — فارقٌ **مقيسٌ ٨.٩×** يعيد التعداد
> من باب آخر. `services/auth._DUMMY_HASH` يغلقه، و
> `test_unknown_student_costs_the_same_time_as_wrong_pin` يحرسه.

| المسار | الطريقة | الغرض | FR |
|---|---|---|---|
| `/me/deck` | GET | البطاقة: رتبة · ساعات · تقدّم · حالة | FR-010 · FR-011 · FR-013 |
| `/me/events` | GET | سجلّ الأحداث شاملًا التصحيحات | FR-012 |
| `/me/readings` | GET | طلبات قراءتي وحالاتها | FR-024 |
| `/me/readings` | POST | إرسال طلب قراءة | FR-020 · FR-021 |
| `/me/tahdir` | GET | تحضيري وتقريري الأسبوعي | FR-093 |
| `/me/tahdir` | POST | تسجيل تحضير يوميّ | FR-090 · FR-091 |

**`GET /me/deck`** — **كل رقم محسوب في الخادم** (NFR: الواجهة تعرض ولا تحسب):
```json
{
  "rank":       { "name": "طيار أول", "tier": 2 },
  "hours":      "612.25",
  "next_rank":  { "name": "رائد سرب", "at_hours": "900.00",
                  "progress_pct": 42.5, "remaining": "287.75" },
  "flight":     { "grounded": false, "last_activity_on": "2026-08-28" },
  "team":       { "name": "سرب الفرقان", "rank_in_org": null }
}
```
- **الرتبة التالية بالنسبة إلى الرتبة لا إلى الساعات.** رصيدٌ سالب بعد تصحيح
  يبقي صاحبه في أدنى رتبة وتاليتُه الثانية — ولو قيست بالساعات لأعادت العتبة
  نفسها فتصير الشريحة صفرًا (قسمة على صفر، أُصلحت في و-١).
- `progress_pct` **داخل الشريحة**: ٦١٢ ساعة نحو «رائد سرب» = **٤٢.٥٪ لا ٦٨٪**
  (ط-٣). الفرق بين الشريحة والمطلق هو أشيع خطأ في شرائط التقدّم.
- في أعلى رتبة: `next_rank: null` ← الواجهة تعرض **رسالة إتمام لا شريطًا ممتلئًا**.
- طالب بلا أحداث: `hours: "0.00"` و`rank.tier: 1` — **حالة مصمَّمة لا مكسورة**.
- طالب بلا عضوية سارية: `team: null` — منقولٌ بين الأسراب يرى بطاقته لا شاشة عطل.

> **`team.rank_in_org` قابل للعدم — وهذا عقدٌ معلَن لا سهو.**
>
> الحقل **ترتيب السرب بالمعدّل**، وهو FR-051 يملكه `services/standings` في
> الوحدة ٩ (`TRACEABILITY.md`). و`/me/deck` يُبنى في الوحدة ١، فيردّ `null`
> حتى ذلك الحين.
>
> **`null` تعني «غير محسوب بعد» لا «لا سرب له».** غياب السرب نفسه يُمثَّل
> بـ`team: null`.
>
> **ولا يُحسب الترتيب داخل `deck` كحلٍّ مؤقّت:** نسخة ثانية من قاعدة الترتيب
> ستفترق عن `standings` عند أوّل تعديل في فكّ التعادل (FR-052)، فيرى الطالب
> رقمين مختلفين لسربه في شاشتين. **الحقل الفارغ أصدق من الرقم المكرَّر.**

**`POST /me/readings`**
```json
→ { "read_on": "2026-08-29", "pages": 40, "book_title": "..." }
← 201 { "id": 88, "status": "pending" }
```
| خطأ | الرمز |
|---|--:|
| طلب مكرّر لنفس اليوم والكتاب | 409 |
| `pages ≤ 0` أو تاريخ مستقبلي | 422 |

**لا ساعات في الردّ** — الطلب لا يمنح شيئًا قبل الاعتماد (FR-021).

**`read_on`** يُحوَّل إلى `occurred_at` **عند الاعتماد** بقاعدة `RULES.md` §٩:
بداية اليوم بتوقيت المنظمة إلى UTC. والتاريخ المستقبلي يُقاس **بتوقيت المنظمة**
لا UTC — وإلا رُفضت قراءةُ مساءِ الخميس في الرياض لأن UTC ما زال في الأربعاء.

**`GET /me/events`** — سجلّ ساعات **الطالب المصادَق عليه**، الأحدث أوّلًا:
```json
{
  "events": [
    { "id": 91, "kind": "reading",    "delta": "6.00",
      "occurred_on": "2026-08-29", "reason": null },
    { "id": 88, "kind": "quran",      "delta": "611.25",
      "occurred_on": "2026-08-28", "reason": null },
    { "id": 84, "kind": "correction", "delta": "-40.00",
      "occurred_on": "2026-08-20", "reason": "خطأ في تصدير راصد" }
  ]
}
```
- `delta` **نصّ عشري** كبقية المبالغ · **والسالب يظهر بإشارته** لا بقيمته المطلقة.
- `reason` **غير فارغ في التصحيحات** (`kind='correction'`) — وهو ما يوجبه ث-٧.
- `occurred_on` **تاريخ وقوع الحدث لا تسجيله**، بتوقيت المنظمة (`RULES.md` §٩).
- **لا معرّف مستخدم في الطلب ولا في المسار:** الهوية من الجلسة.
- قائمة فارغة ⇒ `{"events": []}` بـ`200` — **حالة مصمَّمة لا خطأ**.
- الترقيم `?limit` (افتراضيًّا ٢٠، بحدّ أعلى ١٠٠).

> 🔒 **التصحيحات لا تُخفى** (ط-٤): «إخفاؤها هو ما يثير الشك لا إظهارها». طالبٌ
> يرى رصيده نقص بلا سطر يفسّره يظنّ خللًا أو تلاعبًا — والسطر بسببه يُنهي الشكّ.

**`GET /me/readings`** — طلبات **الطالب المصادَق عليه** وحده، الأحدث أوّلًا:
```json
{
  "readings": [
    { "id": 91, "read_on": "2026-08-30", "pages": 25, "book_title": "…",
      "status": "pending",  "review_reason": null, "reviewed_at": null,
      "hours": null },
    { "id": 88, "read_on": "2026-08-29", "pages": 40, "book_title": "…",
      "status": "approved", "review_reason": null,
      "reviewed_at": "2026-08-31T06:12:00Z", "hours": "6.00" },
    { "id": 84, "read_on": "2026-08-27", "pages": 12, "book_title": "…",
      "status": "rejected", "review_reason": "الكتاب خارج القائمة المعتمدة",
      "reviewed_at": "2026-08-28T09:40:00Z", "hours": null }
  ]
}
```
- `status ∈ ('pending','approved','rejected')`.
- **`review_reason` غير فارغ في `rejected` حصرًا** (ث-٦) — والطالب يراه: رفضٌ
  صامت يقتل الثقة أسرع من غياب الميزة (FR-024).

**`POST /me/tahdir`** — نفس عقد `POST /me/readings` **بالضبط** (`read_on` ·
`pages` · `book_title`)، بقيد إضافيّ واحد (FR-090 · ث-١٨ 🆕):
```json
→ { "read_on": "2026-09-06", "pages": 10, "book_title": "..." }
← 201 { "id": 140, "status": "pending" }
```
| خطأ | الرمز |
|---|--:|
| `read_on` خميس/جمعة/سبت | 422 |
| `pages < 7` | 422 |
| طلب مكرّر لنفس اليوم والكتاب **ولنفس البرنامج** | 409 |

**داخليًّا:** `services/reading.submit(..., activity_type="tahdir")` — نفس
الدالّة القائمة لـ`/me/readings`، بمعامل جديد فقط (`DATABASE.md` §٣.١).
**`kind` على الحدث الناتج `'reading'` كالقراءة العادية** — لا يميَّز تحضير
بـ`kind` مختلف، حفاظًا على حساب «أرضي» القائم بلا تعديل.

**`GET /me/tahdir`** — تحضيري وتقرير الأسبوع الحاليّ (FR-093):
```json
{
  "submissions": [
    { "id": 140, "read_on": "2026-09-06", "pages": 10, "book_title": "…",
      "status": "approved", "hours": "1.50" }
  ],
  "week": {
    "week_start": "2026-09-06",
    "days": [
      { "date": "2026-09-06", "weekday": "الأحد",    "completed": true,  "pages": 10 },
      { "date": "2026-09-07", "weekday": "الاثنين",  "completed": false, "pages": 0 },
      { "date": "2026-09-08", "weekday": "الثلاثاء", "completed": false, "pages": 0 },
      { "date": "2026-09-09", "weekday": "الأربعاء", "completed": false, "pages": 0 }
    ],
    "pages_total": 10,
    "target_pages": 28,
    "percent": 35.7,
    "struggling": true
  }
}
```
- `completed` = **إرسال معتمَد بصفحات ≥٧** — لا معلَّق، ولا أقلّ من ٧ (نفس
  منطق FR-021: لا شيء يُحتسب قبل الاعتماد).
- `percent = pages_total / 28 × 100` — **قد يتجاوز ١٠٠٪** (لا سقف)، **ولا
  علاقة له بعدد الأيام المكتملة مباشرة** (طالبٌ يقرأ ٢٨ صفحة في يوم واحد
  يبلغ ١٠٠٪ رغم يوم واحد «مكتمل»؛ الحقلان يُعرضان معًا لا أحدهما بديلًا عن
  الآخر).
- `struggling` (متعثّر) = `percent < 100` — **بلا هامش تسامح** (قرار مؤكَّد).
- الأسبوع **الحاليّ فقط** — أربعة أيام من `week_starts_on` (الأحد) بلا حقل
  أسبوع في الطلب.
- **`hours` غير فارغ في `approved` حصرًا** (ث-٥)، ونصّ عشري كبقية المبالغ.
  ويأتي **محسوبًا من الحدث** لا من `pages × وزن` في الواجهة (AGENTS ٥).
- **لا معرّف مستخدم في الطلب ولا في المسار:** الهوية من الجلسة، فلا يوجد ما
  يُتلاعب به — وهذا أقوى من التحقّق من الملكية لأنه يُلغي المسار المحتاج إليه.
- قائمة فارغة ⇒ `{"readings": []}` بـ`200` — **حالة مصمَّمة لا خطأ**.

**`GET /boards/pilots`** — صدارة الأفراد (FR-050)، **نافذة الأسبوع الحالي**
(من `orgs.week_starts_on`، لا تراكميّ — نصّ ط-٧ الحرفي):
```json
{ "pilots": [ { "full_name": "أحمد سالم", "hours": "12.50" } ] }
```
**غلاف كائن لا مصفوفة عارية** — اتّساقًا مع كل مسار آخر في هذا المشروع
(`TeamsListSchema`، `ActivitiesListSchema`، ...)؛ لا استثناء هنا رغم أن
الردّ قائمة بحتة. مرتَّبة تنازليًّا بـ`hours`؛ **فكّ التعادل** بـ`id` الطالب تصاعديًّا — استقرارٌ
تقنيّ بحت (منع تذبذب الترتيب بين طلبين متساويين)، لا معيارًا مُعلَنًا: FR-052
يخصّ صدارة **الأسراب** وحدها (نصّه وقصّته ط-٧ لا يذكران الأفراد).

**`GET /boards/teams`** — بالمعدّل لا بالمجموع، **وإلا صار الترتيب قياسًا للحجم**،
نفس نافذة الأسبوع أعلاه:
```json
{ "teams": [ { "team": "سرب الفرقان", "code": "FRQ", "avg_hours": "412.30",
    "members": 6, "readiness": { "flying": 5, "grounded": 1 } } ] }
```
`code` **معروض دائمًا** — هو نفسه معيار فكّ التعادل (أدناه)، فإظهاره شرط
كونه «معلَنًا». `readiness` **عدّاد مجمّع بلا أسماء** — إشارة لوحة الجاهزية المحذوفة كصفحة،
محسوبة باستعلام واحد إضافي (`readiness.flight_states` المجمَّعة — لا حلقة
`flight_state` لكل عضو، وإلا انتهك «استعلام واحد بلا N+1»).
**استعلام واحد بلا N+1** (ط-٧).

**فكّ التعادل (FR-052) — المعيار المُعلَن: `teams.code` تصاعديًّا.** لا نصّ
حرفيّ في أيّ وثيقة يسمّي الحقل؛ قرار Reconcile (٩ب) اختار `code` لا `name`
لأنه **الحقل الوحيد ذو قيد `UNIQUE(org_id, code)`** فعليًّا — فكّ تعادلٍ بحقل
غير مضمون التفرّد ليس فكًّا حتميًّا. «معلَن في الواجهة»: الشاشة تعرض رمز
السرب بجانب اسمه دائمًا، فترتيب الرموز عند تساوي `avg_hours` مرئيّ لا خفيّ.

**`rank_in_org`** في `GET /me/deck` (`schemas/me.py::TeamSchema`، كان مؤجَّلًا
منذ و-٤): موضع سرب الطالب في هذا الترتيب نفسه (١ = الأعلى)، `null` إن كان
الطالب بلا عضوية سارية.

**`GET /boards/formation?scope=team|general`** (افتراضي `team`) — محكوم بـ**ف-١**:
```json
{ "scope": "team",
  "aircraft": [ { "name": "...", "size": "611.25", "size_pct": 100, "grounded": false } ] }
```
`size_pct` (٠-١٠٠، الأكبر بين أسطول هذا الردّ = ١٠٠) **جاهز للعرض مباشرةً** —
نفس نمط `next_rank.progress_pct` في `GET /me/deck`: الواجهة تكتب
`` `${size_pct}%` `` بلا عملية حسابية، لأن `check-no-domain-logic.mjs` يمنعها
حرفيًّا في ملفّات مستهلكة العقد.
| النطاق | المجموعة | يُعرض |
|---|---|---|
| `team` (افتراضي) | أعضاء سرب الطالب المصادَق عليه وحده | **الأسماء كاملة** شاملة الساقطين |
| `general` | كل طيّار نشط في المنظمة | `name: null` لكل ساقط — **إنجاز فقط** |

**`size` تراكميّ لا نافذة أسبوع** — عمدًا مخالف لصدارتَي `/boards/pilots`
و`/boards/teams`: نصّ ط-٨ («حجم الطائرة = ساعاتها») لا يذكر «الأسبوع»
إطلاقًا خلافًا لِط-٧ الذي يذكرها صراحةً، والمشهد سرديّ («تشكيل» ينمو) لا
تنافسيّ دوريّ — طائرة تتقلّص كل أحد إلى الصفر تُناقض فكرة النموّ. نفس تعريف
`hours` في `GET /me/deck` تمامًا (`SUM(delta)` الكلي، `scope='individual'`).

`scope=general` بلا عضوية سارية للطالب: يُردّ بلا خطأ (نفس نمط `team: null`
في `GET /me/deck`) — لا معنى لـ«سربي» لمن لا سرب له، لكنّ المشهد العام لا
يعتمد عضويته أصلًا.

**`GET /questions/today`** — «اليوم» بتوقيت المنظمة لا المتصفّح
(`orgs.timezone`، لا نافذة أسبوع هنا — يوم واحد فقط):
```json
← 200 { "question": {
    "id": 5, "prompt": "...",
    "choices": [ { "id": 1, "text": "..." }, { "id": 2, "text": "..." } ],
    "answered": null } }
```
- **لا `correct_id` ولا `note` قبل الإجابة** — كشفهما يُفسد السؤال نفسه.
- **بلا سؤال اليوم:** `{ "question": null }` — حالة مصمَّمة (نمط `team: null`
  في `GET /me/deck`)، لا `404`: عدم وجود سؤال ليس خطأ الطالب.
- **بعد الإجابة**: `answered` يحمل نفس شكل ردّ `POST .../answer` أدناه —
  **الجواب الصحيح وشرحه يظهران دائمًا**، فإعادة فتح الشاشة لا تُخفيهما.
  ```json
  "answered": { "choice_id": 2, "correct": false, "correct_id": 3,
                "note": "الشرح...", "awarded_hours": "0.00" }
  ```

**`POST /questions/{id}/answer`**
```json
→ { "choice_id": 2 }
← 200 { "correct": false, "correct_id": 3, "note": "الشرح...",
        "awarded_hours": "0.00" }
```
- **الجواب الصحيح وشرحه يظهران في الحالتين** — الخطأ فرصة تعلّم لا عقوبة (ط-٦).
- إجابة ثانية → **409** بقيد `UNIQUE(user_id, question_id)` في القاعدة، **لا
  بإخفاء الزر**.
- «اليوم» **بتوقيت المنظمة لا المتصفّح**.
- **المكافأة `daily_questions.reward_hours` مباشرةً — لا عبر `rules/engine`**
  (قرار Reconcile و-٩ج): خاصّية هذا السؤال بعينه، لا وزن نشاط عامّ. حدث دفتر
  `kind='daily_question'` **يُكتب فقط إن صحّت الإجابة**؛ الخطأ لا يكتب شيئًا
  (`awarded_hours` تُعرض `"0.00"` لأن لا شيء مُنح، لا لأن حدثًا بقيمة صفر كُتب).
- `choice_id` غير موجود بين خيارات السؤال ⇒ `422`.
- **بلا سؤال اليوم لهذا `id`، أو `id` يخصّ يومًا آخر:** `404` — لا إجابة على
  سؤال غير موجود.
- **ذرّية الكتابة (و-٩د، ث-١٧):** صفّ `answers` وحدث الدفتر يلتزمان بـ`commit`
  واحد (`ledger.append_pending` يُثبَّت لا يُلتزَم، ثم `answers.point_event_id`
  يُربَط، ثم التزامٌ واحد ينهي الاثنين معًا) — لا نافذة عطل بينهما. **ودفاعٌ
  ثانٍ في القاعدة**: `CHECK` يمنع أي إجابة صحيحة بلا `point_event_id`، أو
  خاطئة تحمله، بصرف النظر عن مسار الكتابة.

**`POST /notes`**
```json
→ { "body": "..." }
← 201 {}
```
**لا `id` يُعاد** — معرّف يعود للمرسِل يخلق خيط ربط حيث وعدنا ألّا يكون.
الجهالة **بنية الجدول** (§٣ في `DATABASE.md`). `day` يُشتقّ من الخادم
(«اليوم» بتوقيت المنظمة، لا الثانية — ط-٩: الثانية تكشف المرسِل بمقارنة
سجلّ الدخول)، **لا يُقبل من الطلب**.

**`GET /week/pilot`** — طيار الأسبوع الحالي وسببه (FR-062):
```json
← 200 { "pilot": { "full_name": "أحمد سالم", "reason": "ثبات حضوره..." } }
```
- **بلا اختيار لهذا الأسبوع بعد:** `{ "pilot": null }` — حالة مصمَّمة (نمط
  `team: null`)، لا `404`.
- «الأسبوع» بنفس تعريف `orgs.week_starts_on` في `/boards/*` تمامًا —
  اتّساق نافذة واحدة عبر كل المشهد الاجتماعي.

**`POST /admin/week/pilot`** — اختيار طيار الأسبوع (FR-062 · م-٦):
```json
→ { "user_id": 7, "reason": "ثبات حضوره وتقدّمه الملحوظ هذا الأسبوع." }
← 201 { "user_id": 7, "full_name": "أحمد سالم", "week_start": "2026-08-02" }
```
- `reason` **نصّ حرّ إلزاميّ** — فارغ أو غياب ⇒ `422` (ط-١٠: «القيمة كلها في
  لماذا لا في الاسم»).
- اختيار ثانٍ لنفس الأسبوع ⇒ `409` بقيد `UNIQUE(org_id, week_start)` (ث-٩) —
  لا تحديثًا للاختيار الأوّل؛ تغيير الاختيار قرارٌ يستحقّ مسارًا صريحًا لا
  حقلًا يُستبدَل ضمنيًّا (نمط أرشفة السرب م-١٠).

**`GET /admin/notes`** — الملاحظات (م-٥):
```json
← 200 { "notes": [ { "id": 12, "body": "...", "day": "2026-08-20",
                      "read_at": null } ] }
```
الأحدث أوّلًا. **بلا مصدر ولا قناة ردّ** — لا `user_id` ولا `ip` في الجدول
أصلًا (ث-١٢)، فلا وجود لهما هنا مهما كانت الصلاحية.

**`PATCH /admin/notes/{id}`** — تعليم مقروءة، **لا حذف** (م-٥):
```json
→ { "read": true }
← 200 { "id": 12, "read_at": "2026-08-21T09:00:00Z" }
```
`read` **`true` وحدها ذات معنى** — لا تراجع عن «مقروءة» (نمط أرشفة السرب
`ArchiveTeamSchema`: قرار أحاديّ الاتّجاه لا حقل بقيمتين).

**`GET /station`** — محطة التزوّد (FR-072). **قرار مؤرَّخ (و-٨):** رغم أنها
تحت `POST /admin/fuel/assess` في `TRACEABILITY.md`، هي شاشة **طيّار** لا مشرف —
`@login_required` لا `@admin_required` — لأن م-٧ عن *تقييم* المشرف، أمّا *عرض*
الوقود فحقّ كل عضو في سربه (تناظر `/boards/*` و`/questions/*` في هذا القسم
تمامًا لا §٦). الهوية والسرب من الجلسة — لا معرّف سرب في الطلب:
```json
← 200 {
  "team": { "name": "سرب الفرقان", "litres": "340.00" },
  "tank_capacity_l": "500.00",
  "recent": [
    { "activity_name": "الحفظ الجماعي", "occurred_on": "2026-08-20",
      "total_pct": "93.50", "litres": "46.75" }
  ]
}
```
- `team: null` إن كان الطيار بلا عضوية سارية — **حالة مصمَّمة لا مكسورة**
  (`SCOPE.md` ط-٢)، بنفس عقد `team: null` في `GET /me/deck`.
- `litres` **تراكميّ** لا نافذة — `SUM(delta) WHERE scope='team'` للسرب.
- `recent` آخر ١٠ تقييمات (الأحدث أوّلًا) — **تفصيل يشرح الرقم** (FR-071)، لا
  مجموع صامت.

**لا يكتب شيئًا** (ق-١٩٢):
```

← 200 {
  "batch_id": "305d0f70…",
  "duplicate_warning": false,
  "duplicate_imported_at": null,
  "rows": [
    { "name": "سلمان الغفيص", "match_status": "matched", "user_id": 7,

      "attendance": "2", "tasmi3_days": "2" },

      "tasmi3_days": "0" }

```
| الحقل | لماذا |
|---|---|
| `match_status` | `matched` (تطابق تامّ واحد) · `ambiguous` (أكثر من مرشّح — ق-١٨٠) · `unmatched` (لا مرشّح) — الأخيران **لا يُطبَّقان تلقائيًّا** (ق-١٧٩/١٨٠) |
| `percentages` | محسوبة داخليًّا **دائمًا** (منجز/مستهدف×١٠٠، مقرَّبة للعرض فقط) — عمود «نسبة X» في الملفّ **مُتجاهَل** (ق-١٨٢) |
| `duplicate_warning` | تحذير بمجموع اختباري (checksum) — **لا يمنع** الاعتماد (ق-١٩٠، قرار #٩) |
| **الترويسة إلزامية بالعدد والترتيب** | عمودان متبادلان بصمت = أرقام معقولة الشكل خاطئة تمامًا (ق-١٧٥) |

**`POST /admin/paste/commit`** — نفس حمولة المعاينة (الملفّ يُعاد إرساله،
نمط `thresholds/preview`↔`thresholds` القائم — لا حالة خادم بين النداءين)

```
  · name_resolutions={"عبدالله السالم": 12}          (JSON، اختياري)
  · value_overrides={"سلمان الغفيص": {"hifz_achieved": "8"}}  (JSON، اختياري)
← 201 {
  "batch_id": "305d0f70…",
  "events_created": 3,
  "rows": [
    { "name": "سلمان الغفيص", "status": "resolved", "user_id": 7,
      "categories": {
        "hifz": {"status": "created", "hours": "80.00"},
        "thabat": {"status": "already_imported"},
        "muraja3a": {"status": "skipped_zero", "hours": "0.00"},
        "attendance": {"status": "created", "hours": "6.00"}

    { "name": "لا أحد بهذا الاسم", "status": "unmatched", "user_id": null }
  ]

```

|---|---|
| **`raw_rows` يُكتب دائمًا** لكل صفّ طالب حقيقيّ، بصرف النظر عن حالة المطابقة | FR-033 — الخام مرجعٌ لإعادة الحساب المستقبلية (FR-086) لا يعتمد نجاح المطابقة |
| **لا التزام ذرّي على مستوى الدفعة كلّها** | إعادة استيراد مصحَّحة لبعض الطلاب فقط يجب أن تبقى ممكنة (`docs/slices/و-٥.md` §٢.١ب) — `already_imported` يُستبعَد صراحةً بدل رفض الدفعة |

| `value_overrides` تُسجَّل في `audit_log` (القيمة الأصلية والمعدَّلة معًا) | FR-037 نفسه — تعديلٌ بلا أثر تدقيق يبدو تلاعبًا |
| تصحيح قيمة **مستوردة سابقًا** خطأ | ليس عبر إعادة الاستيراد — عبر `/admin/quran/entry`/`reverse` القائمين (ADR-004) |

**`POST /admin/events/{id}/reverse`**
```json
→ { "reason": "خطأ في تصدير راصد — صفحات مضاعفة" }
← 201 { "id": 5012, "delta": "-40.00", "kind": "correction" }
```

> `reason` **إلزامي**. `422` بدونه. تصحيحٌ بلا سبب يبدو تلاعبًا في بطاقة الطالب.
> و**لا `UPDATE` ولا `DELETE`** — هذا هو ما يجعل مرونة التعديل الكاملة ممكنة
> بلا فقدان التاريخ. `id` من منظمة أخرى أو غير موجود ⇒ `404`. **تصحيح حدثٍ
> هو نفسه حدثٌ قابل للتصحيح** — لا حارس يمنع تصحيح تصحيح (سابقة قائمة منذ
> و-١، `test_deck.py::test_double_correction_shows_negative_balance`؛
> `ledger.reverse()` عام على أي `PointEvent` بصرف النظر عن `kind`ه). و**يكتب
> `audit_log` بـ`kind='quran_correction'`** ذرّيًّا مع الحدث (FR-037).

**`GET /admin/quran/students`** — لملء قائمة اختيار الهدف:
```json
← 200 { "students": [ { "id": 7, "full_name": "أحمد سالم" } ] }
```
**نفس فلترة `services/entry._roster`**: مستخدِمون نشِطون بعضوية سارية،
**على مستوى الجمعية كلّها** (§٧.٣) لا فريق المشرف وحده.

**`GET /admin/quran/events?user_id=7`** — أحدث ٢٠ حدثًا لطالب، ليختار
المشرف أيّها يُصحَّح:
```json
← 200 { "events": [
  { "id": 5012, "kind": "quran", "delta": "10.00",
    "occurred_on": "2026-08-20", "reason": null }

```
`user_id` من منظمة أخرى أو غير موجود ⇒ `404`. **قراءة خالصة** —
`services/deck.recent_events` نفسها التي تخدم `GET /me/events` (FR-012).

**`POST /admin/quran/entry`**
```json
→ { "user_id": 7, "occurred_on": "2026-08-20", "activity_type": "memorize",
    "quantity": "3", "mastery": "mastered",
    "reason": "غاب عن تصدير راصد هذا الأسبوع" }
← 201 { "id": 5099, "delta": "7.50", "kind": "manual" }
```
| القرار | لماذا |
|---|---|
| `reason` **إلزامي** | `422` بدونه — نفس منطق `reverse` (ADR-004)، مفروض في القاعدة أيضًا (ث-٧ موسَّعة) |
| `mastery` **اختياري** | `Achievement.mastery` نفسه اختياري في `rules/engine` — غيابه multiplier=١ |
| `delta` **محسوبة لا مُدخَلة** | تمرّ بـ`rules/engine.hours_for` كأي إنجاز (AGENTS ٥ · لا حساب خارج المحرّك) |
| `activity_type` **بلا وزن ساري** وقت `occurred_on` | `422` برسالة `rules/engine` نفسها — لا `500` |
| `occurred_on` **مستقبليّ** | رفض — نفس قيد `SubmitReadingSchema.read_on` |
| `user_id` من منظمة أخرى | `404` |
| **بلا `raw_row_id`** | مستقلّ عن اللصق تمامًا — انظر تصحيح `DATABASE.md` |

**كلا المسارين يكتبان `audit_log` بـ`kind='quran_correction'`** ذرّيًّا مع
الحدث نفسه (FR-037): `ledger.append_pending()` (`flush` لا `commit`، نمط
ث-١٧) ثم `audit.record()` ثم `commit` واحد — فشلٌ في أيّهما **لا يترك حدثًا
يتيمًا بلا أثر تدقيق**.

**`POST /admin/tahdir/entry`** — إضافة مباشرة معتمَدة فورًا، بلا مرور بحالة
معلَّقة (نمط `POST /admin/quran/entry`، و-٦):

  العادية أيضًا لو احتاجها المشرف مستقبلًا (`"reading"`).
- نفس قيود `/me/tahdir` (يوم الأسبوع لو `tahdir` · `pages≥7` لو `tahdir` ·
  لا تاريخ مستقبليّ) تُفحَص هنا أيضًا — **لا استثناء إداريّ** لهذه القواعد.
- **يكتب `audit_log`** بـ`kind='reading_admin_entry'` ذرّيًّا مع الحدث
  (`ledger.append_pending` + `audit.record` + `commit` واحد، نفس نمط
  `services/quran.add_entry`) — إضافة نيابةً عن طالب فعلٌ يستحقّ أثرًا مرئيًّا
  في سجلّ التغييرات (FR-084) رغم عدم ورودها صراحةً في نصّ FR-092.

**`GET /admin/tahdir/report`** — تقرير أسبوعي **لكل طلاب الجمعية** (FR-093):

**`GET /admin/attendance`** — قائمة السرب وحالة الأسبوع الحالي (FR-041):
```json
← 200 { "week_start": "2026-08-30", "already_recorded": false,
        "pilots": [ { "user_id": 3, "full_name": "أحمد سالم" } ],
        "absent_user_ids": [], "undo_until": null }
```
`already_recorded=true` تعني أن الحضور سُجِّل لهذا الأسبوع أصلًا —
`absent_user_ids` تعرض من عُلِّم غائبًا وقتها، و`undo_until` وقت انتهاء
مهلة التراجع (`null` إن انتهت فعلًا فلا زرّ تراجع يُعرض).

**`POST /admin/attendance`** — **الجميع حاضر افتراضًا** (FR-041 الحرفي:
«تفتح والجميع معلَّم حاضرًا»)، فالطلب يحمل الغائبين فقط:
```json
→ { "absent_user_ids": [3, 7] }
← 201 { "present": 12, "absent": 2, "hours_each": "3.00",
        "undo_until": "2026-08-30T10:35:00Z" }
```
- الأسبوع **الحالي فقط** (نفس نافذة `standings.py`/`week/pilot`) — لا حقل
  أسبوع في الطلب، ولا رجوعًا لتسجيل أسبوع ماضٍ من هذه الشاشة الاحتياطية.
- **الحضور نشاط في جدول الأوزان كأي نشاط آخر** (ف-٦) — يمرّ من
  `rules/engine` بـ`quantity=1`، لا رقمًا مكتوبًا في الكود. وزنه غائب عن
  منظمة ما (نادر، لكنه ممكن) ⇒ `422`.
- **idempotency بلا جدول جديد** (FR-042، نمط ث-٣ القائم في `point_events`
  أصلًا): كل حدث حضور يحمل `external_ref` حتميًّا
  (`attendance:{week_start}:{user_id}`)، فإرسال الدفعة مرّتين لنفس الأسبوع
  يصطدم بقيد `uq_event_external_ref` القائم ⇒ **`409`** — لا حاجة لقيد جديد
  ولا جدول حضور مستقلّ.
- **معاملة واحدة** (FR-042): كل أحداث الحاضرين تُلحق بـ`ledger.append()`
  دفعةً واحدة — إمّا كلّها أو لا شيء.

> **`fuel_activities`/`fuel_criteria` بلا قصّة FR مستقلّة** — م-٧ يفترض
> وجودهما. `POST /admin/fuel/activities` **بنية تحتية ضرورية لتشغيل FR-070
> فعليًّا** (قرار مؤرَّخ، و-٨) — بلا مسارٍ لإنشاء نشاط، «أقيّم نشاطًا» جملة
> بلا مرجع. تُبنى **بأقلّ سطح ممكن**: إنشاء يجمع النشاط وبنوده في طلب واحد،

**`GET /admin/fuel/activities`** — الأنشطة غير المؤرشَفة وبنودها:
```json
← 200 { "activities": [
  { "id": 1, "key": "group_memorize", "name": "الحفظ الجماعي", "litres_full": "50.00",
    "criteria": [ { "id": 1, "key": "attendance", "name": "الحضور", "weight_pct": "40.00" },
                  { "id": 2, "key": "quality", "name": "الجودة", "weight_pct": "60.00" } ] }
] }
```

**`POST /admin/fuel/activities`** — إنشاءٌ **جديد** لا تعديل على نشاط قائم:
```json
→ { "key": "group_memorize", "name": "الحفظ الجماعي", "litres_full": "50",
    "criteria": [ { "key": "attendance", "name": "الحضور", "weight_pct": "40" },
                  { "key": "quality", "name": "الجودة", "weight_pct": "60" } ] }
← 201 { "id": 1 }
```
`422` إن كان مجموع `weight_pct` ≠ ١٠٠ بالضبط — **ث-١٠أ**، في الخدمة والقاعدة معًا.

**`POST /admin/fuel/assess`** — تقييمٌ **جديد**، لا تعديل على تقييم قائم.
`team_id` صريح في الجسم — **المشرف على مستوى الجمعية** يقيّم أيّ سرب (§٧.٣)،
لا سربه وحده:
```json
→ { "team_id": 1, "activity_id": 1, "occurred_on": "2026-08-20",
    "scores": [ { "criterion_id": 1, "score_pct": "100" },
                { "criterion_id": 2, "score_pct": "90" } ],
    "note": "ملاحظة اختيارية" }
← 201 { "id": 12, "total_pct": "94.00", "litres": "47.00" }
```
| الرفض | لماذا |
|---|---|
| `422` — مجموع `weight_pct` **للبنود المُرسَلة فعلًا** ≠ ١٠٠ | **ث-١٠ب**: انجراف بين تعريف النشاط ولحظة التقييم — نشاطٌ سليم عند الإنشاء قد يُفسَد لاحقًا |
| `422` — بندٌ لا ينتمي لهذا النشاط | تقييم بند نشاط آخر بالخطأ |
| `409` — نفس السرب ونفس النشاط ونفس `occurred_on` مقيَّمان من قبل | `uq_fuel_assessment_per_day` |

**الأوزان تجمع ١٠٠٪ بالضبط** — حرسًا مزدوجًا (ث-١٠أ عند تعريف البنود ·
ث-١٠ب عند التقييم لا مرحلة واحدة): نشاطٌ أوزانه ٩٥ يجعل الإتقان الكامل ٩٥٪،
**فيظنّ السرب أنه قصّر وهو أتقن**.

`total_pct = Σ(score_pct × weight_pct) / 100` · `litres = total_pct/100 × litres_full`.
**الدرجات تُحفظ مفصّلة** (`fuel_scores`) ليُشرح الرقم لاحقًا (FR-071) ·
`occurred_on` **تاريخ الوقوع لا الإدخال** يُحوَّل إلى UTC بتوقيت المنظمة
(`RULES.md` §٩) · **يُسجَّل في `audit_log`** بـ`kind='fuel_assessment'`.

(`RULES.md` §٩) — نفس تحويل `reading.occurred_at_for`، لا آلية موازية.

`after` يحمل معرّف الإصدار وتاريخ سريانه — **بلا نسخ كل الأوزان** (`before`/`after`
ملخّص لا نسخة كاملة، فرقٌ متعمَّد عن `pin_reset` الفارغَين تمامًا).

**`POST /admin/thresholds/preview`** — من يرتفع ومن ينخفض **قبل** الحفظ، بلا

تحت عتبة أقدم. التفصيل الكامل: `docs/slices/و-٧.md` §الرتب لا تنخفض.

| `422` — مفتاح `key` قائم غائبٌ عن الإرسال | حذف رتبة يتيّم كل من بلغها — لا حذف، إضافة فقط |

**`GET /admin/report`** — ملخّص دوري **مشتقّ من سجلّ الأحداث بلا جدول جديد**:
```json

  "totals": { "hours": "128.50", "active_pilots": 4, "grounded_pilots": 1 },
  "teams": [
    { "id": 1, "name": "سرب الفرقان", "hours": "128.50",

  ],
  "top_movers": [
    { "user_id": 3, "full_name": "ماجد القحطاني", "hours": "90.00" }
  ],
  "grounded": [
    { "user_id": 4, "full_name": "فهد الدوسري", "last_activity_on": "2026-07-31" }
```

- `avg_hours` **معدّل لا مجموع** — اتّساقًا مع صدارة الأسراب (FR-051): المجموع

- **بلا جدول جديد ولا كتابة** — استعلامات قراءة على `point_events` و`memberships`.

| `404` — الطالب غير موجود أو من منظمة أخرى | رسالة واحدة — نفس علّة `reset-pin` |

**العضوية القديمة تُغلَق (`left_at=الآن`) لا تُحذَف، والجديدة تُفتح** — **النقل
لا ينقل التاريخ** (م-١٠): أحداث الطالب في `point_events` تبقى منسوبة كما وقعت،
فلا يقفز سربه الجديد في الترتيب بحدث لم يصنعه أعضاؤه. والدور **يُحمَل معه** —
مشرفٌ يبقى مشرفًا بعد النقل، لأن صلاحيته على مستوى الجمعية لا السرب (§٧.٣).

**الثلاثة تُسجَّل في `audit_log`** بـ`kind` بالترتيب `team_created` ·
`team_archived` · `membership_transferred`.

**`GET /admin/audit`** — **مفتوح لكل المشرفين لا لمالك المنظمة وحده.** هذا هو
التعويض الكامل عن دمج الدورين (`SCOPE.md` §٣.٣): الحماية **كشف الاستعمال** لا
**منع الصلاحية**. سجلٌّ يراه واحد فقط لا يحمي من شيء.
```json
← 200 { "entries": [
  { "id": 41, "kind": "thresholds_update", "summary": "تحديث سُلّم الرتب",
    "actor_name": "بندر الشمري", "at": "2026-09-01T12:00:00Z" }
] }
```
**فارغة صراحةً لا خطأ:** منظمة بلا تغييرات بعد ترجع `{"entries": []}` بـ`200` —
**معيار قبول قائم بذاته** (FR-084)، لا سلوكًا مفترَضًا: شاشةٌ تعرض «لا تغييرات
بعد» لا رسالة عطل ولا لوحًا فارغًا صامتًا. `before`/`after` **لا يظهران هنا
عمدًا** — قائمة مسح لا محرّر: من يحتاج التفصيل يفتح السطر (خارج نطاق و-٧).

**`POST /admin/recalc`** → `{ "dry_run": true }` **افتراضيًّا**. الردّ يعرض
التسويات قبل تطبيقها، **ولا يُحذف شيء أبدًا** — تُصدَر أحداث تسوية.

> ### تصحيح مقصود — `FR-004` صار مسارًا مستقلًّا
>
> **كان:** «يُغطّى ضمن `PATCH /admin/teams` — لا يستحقّ مسارًا مستقلًّا».
> **صار:** `POST /admin/users/{id}/reset-pin`.
>
> | لماذا | |
> |---|---|
> | **أمنيًّا** | فعلٌ **يُبطل كل جلسات مستخدم** يجب أن يكون صريحًا في العقد، لا حقلًا مدفونًا في `PATCH` عامّ — فلا يُطلَق عرَضًا بتغيير لاحق في مسار الأسراب |
> | **حدود الوحدات** | مسارٌ مشترك بين `FR-004` (و-٢) و`FR-083` (و-٧) يخلق **تبعية متقاطعة**: تغييرٌ في مسار و-٧ يكسر متطلَّب و-٢ صامتًا. والاستقلال هو ما يجعل ترتيب الوحدات مرنًا |
>

> يتّضح أن الفعل أمنيّ لا إداري.
