# النشر — دليل عمليّ

> **صدقٌ أوّلًا:** كل أمر أدناه **اختُبر شكله محليًّا** (`docker-compose.yml`
> وهجرةٌ ودخولٌ حيّ)، لكن **التشغيل على خادم سحابيّ حقيقيّ لم يحدث بعد** —
> لا أحد يملك بيانات اعتمادك هنا. فجرّبه على نطاق ضيّق (طالبَين-ثلاثة) قبل
> الإعلان للجميع.
>
> وتصحيحٌ لِما كان مكتوبًا هنا خطأً حتى و-٢١: كانت هذه الوثيقة تقول «إنشاء
> المنظمة والطلاب الحقيقيين يقع عبر شاشات المشرف نفسها بعد أوّل نشر». **لم
> يكن ذلك صحيحًا** — لم يوجد مسارٌ واحد يُنشئ جمعيةً ولا طالبًا إلا
> `seed.py` (وهو يرفض الإنتاج). و-٢١ بنى الناقص: `flask bootstrap-org`
> وشاشة «الطلاب». أمّا الزعم القديم فمثالٌ على أسوأ خطأ في وثيقة نشر —
> يُكتشَف بعد النشر لا قبله.

## ١. القرار — ولماذا ليست Vercel

**الموصى به: خادمٌ واحد يشغّل `docker-compose.prod.yml` على Oracle Cloud
Always Free بمنطقة جدّة (`me-jeddah-1`).** التفصيل الكامل في
`docs/decisions/ADR-010-deployment-platform.md`، وخلاصتُه:

| | |
|---|---|
| **التأخير** | جدّة داخل المملكة: ~١٠–٢٠ms من الرياض مقابل ~٩٠–١٢٠ms من أوروبا. وجمهورنا طلابٌ على الجوّال |
| **التكلفة** | مجانًا للأبد (٤ OCPU ARM / ٢٤GB ≈ ٥٠× حاجتنا) — ومجّانيةٌ دائمة تُلغي نمطَ عطلٍ حقيقيّ: فاتورةٌ تُنسى فيسقط الموقع |
| **المطابقة** | يشغّل ملفّاتنا كما هي، بلا سطرٍ مختلف |

**و‍Vercel مرفوضة** لخمسة أسباب من معمارية هذا المشروع، أهمُّها ثلاثة:
التطبيق عمليةٌ طويلة العمر بمجمّع اتصالات (والدوالّ بلا خادم تُنتج عاصفة
اتصالات على Postgres) · والواجهة والـAPI من **أصلٍ واحد** عن قصد، وأيُّ
فصلٍ يُعيد CORS ويُرخي فحصَ `Origin` (ADR-006) · ولا طرفية، فلا
`flask db upgrade` ولا `flask bootstrap-org`.

**والبديل إن لم يتفرّغ أحدٌ لإدارة خادم: Render (~$١٤/شهر)** — نفس
`Dockerfile`، وقاعدةٌ مُدارة بنسخٍ تلقائية، ونشرٌ تلقائيّ من GitHub، وصفر
صيانةِ نظام. والمستودع يحمل `render.yaml` فالنشر ثلاث نقرات: **New ⇒
Blueprint**. ومقايضته: الطبقة المجانية تنام بعد ١٥ دقيقة خمول وقاعدتُها
المجانية لها مدّة — فالتجربةُ عليها والتشغيلُ الحقيقيّ على الطبقة المدفوعة.

> **والمقايضة الحقيقية ليست المال بل من يَحرُس الخادم.** ولذلك خُفِّضت كلفةُ
> الحراسة إلى ما يقارب الصفر: تحديثاتٌ أمنية تلقائية · جدار · **تدوير
> سجلّات** (امتلاءُ القرص أشهر أسباب سقوط الخوادم الصغيرة) · فحصُ صحّة يلمس
> القاعدة فيُعيد التشغيل تلقائيًّا · عاملٌ معلَّق يُقتَل ويُستبدَل · نسخٌ
> احتياطيّ **مُجدوَل** يرفض النسخة الفارغة · ونشرٌ من CI بلا يد.

## ٢. التشغيل — أمرٌ واحد

على خادم Ubuntu جديد:

```bash
curl -fsSL https://raw.githubusercontent.com/Mohammed2254/ALASRAB/main/deploy/bootstrap.sh | bash
```

يثبّت دوكر · **يصلّب الخادم** (تحديثات تلقائية · UFW · سقف سجلّات) ·
يستنسخ الكود · **يتوقّف ويطلب `.env.prod` بيدك** · يبني ويشغّل · يطبّق
الهجرات · يجدول النسخ الاحتياطيّ · ويدلّك على أمر التأسيس.

**ولا يولّد سرًّا ولا يطبعه:** سكربتٌ يطبع كلمة مرور يُسرّبها إلى تاريخ
الأوامر.

### الأسرار — بيدك لا بيد السكربت

```bash
cd ~/asrab-v2
cat > .env.prod << 'EOF'
DB_PASSWORD=<كلمة مرور طويلة عشوائية>
SECRET_KEY=<الناتج أدناه>
DOMAIN=<نطاقك، أو اتركه مع نفق Cloudflare>
EOF
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

**ولا يُلمَس `docker-compose.prod.yml` لوضع سرٍّ فيه أبدًا** — كل قيمة من
`.env.prod` وحده (`NFR-09`)، وهو مُستبعَد من Git تلقائيًّا. وحرسُ الإقلاع
**يرفض التشغيل** بمفتاحٍ تطويريّ أو `CORS` فارغة — فالإعداد الناقص يُرى في
سجلّ النشر لا بعد أسبوع.

### طبقة HTTPS — واحدةٌ لا اثنتان

الدخول يستعمل كوكي `Secure`، فلا يعمل بلا HTTPS حقيقيّ. في
`docker-compose.prod.yml` خيارَان، **فعِّل واحدًا**:

- **عندك نطاق** (سجلّ A يشير للخادم): `caddy` مفعَّلة افتراضيًّا — الشهادة
  تُصدَر عند أوّل تشغيل.
- **بلا نطاق:** عطِّل `caddy` وفعِّل `cloudflared`، ثم:
  ```bash
  docker compose -f docker-compose.prod.yml logs cloudflared | grep trycloudflare
  ```
  HTTPS حقيقيّ بلا نطاق وبلا منفذٍ مفتوح (اتصالٌ صادرٌ فقط). **والرابط
  يتغيّر كل إعادة تشغيل** — للتجربة لا للإعلان.

### النشر التلقائيّ بعدها

`.github/workflows/deploy.yml` ينشر عند **نجاح CI** لا عند الدفع. ثلاثة
أسرار في Settings ⇒ Secrets and variables ⇒ Actions:

| | |
|---|---|
| `DEPLOY_HOST` | عنوان الخادم |
| `DEPLOY_USER` | المستخدم (في مجموعة `docker`) |
| `DEPLOY_SSH_KEY` | مفتاحٌ خاصّ **للنشر وحده**، لا مفتاحك الشخصيّ |

**ولا يُشغّل الهجرات** — بل **يرفض النشر** إن كانت ثمّة هجرة معلَّقة ويقول ما
يجب فعله، فيبقى الكود القديم يعمل على مخطّطه الصحيح. وهو أسلم من جديدٍ
يصطدم بعمودٍ غير موجود، ويحفظ قرار `ARCHITECTURE.md §٨`.

## ٣. التأسيس — الخطوة التي بلا شيءٍ قبلها

قاعدةٌ جديدة فارغة: لا جمعية ولا مشرف ولا طالب. وهذا الأمر هو **المدخل
الوحيد**، ويعمل على قاعدةٍ فارغة وحدها ويرفض الثانية:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  run --rm app flask bootstrap-org
```

يسأل عن اسم الجمعية وأوّل سرب واسم المشرف ورقم دخوله، ثم يطبع **رمزًا من
أربعة أرقام مرّةً واحدة**. اقرأه واحتفظ به — لا يُخزَّن نصًّا ولا يُعرض ثانيةً.

**ولماذا أمرُ طرفية لا شاشةُ تسجيل؟** مسارٌ عامّ يُنشئ جمعيةً ومشرفًا هو بابٌ
لمن يسبقك إليه. والطرفية داخل الحاوية صلاحيتُها صلاحيةُ الخادم نفسه — فلا
سطح هجوم جديد.

> **ولا بذرة تجريبية هنا:** `seed.py` بيانات وهمية للتطوير وحده، ورمزُها
> `1234` للجميع — وهو **يرفض الإقلاع** على بيئةٍ تبدو إنتاجًا أصلًا.

## ٤. الطلاب — من أين يأتون

من شاشة **الإدارة ⇒ الطلاب** بعد الدخول:

- **طالبٌ واحد**: اسم + رقم دخول ⇒ يولّد الخادم رمزه ويعرضه مرّة.
- **لصق قائمة**: سطر لكل طالب (`الاسم, رقم الطالب`) — الفاصلة أو التبويب.
  **والسطر الفاشل يُبلَّغ عنه وحده ولا يُسقط بقيّة اللصقة.** الرموز كلّها
  تُعرض مرّةً واحدة في بطاقةٍ لا تُغلق بنفسها.
- **لا حذف — تعطيل**: الحذف يتيّم أحداث الطالب في الدفتر (ADR-004).
  والتعطيل يُبطل جلساته فورًا، فكوكي عمرُه تسعون يومًا لا يبقى حيًّا.

ثم **الأوزان** و**العتبات**: القيم الأوّلية مؤلَّفة عن قصد (ف-٨) — تُعاد
معايرتها بعد شهر بيانات حقيقية، والصفر مشروع لتعطيل نشاط.

## ٥. التحديث لاحقًا

**الطريق المعتاد: لا شيء.** تدفع إلى `main`، فيعمل CI، وينشر `deploy.yml`
تلقائيًّا ويتحقّق من الصحّة قبل أن يعدّ النشر ناجحًا.

**ويتوقّف وحده إن كانت الدفعة تحمل هجرة** — فتُطبّقها بيدك ثمّ تُعيد تشغيل
الإجراء (**Run workflow**):

```bash
cd ~/asrab-v2
docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm app flask db upgrade
```

وإن أردتَ النشر يدويًّا بلا CI:

```bash
cd ~/asrab-v2 && git pull --ff-only
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

الهجرة **يدويّة دائمًا** ولا تُشغَّل تلقائيًّا عند إعادة تشغيل الحاوية
(`ARCHITECTURE.md §٨`).

## ٦. النسخ الاحتياطي

```bash
./deploy/backup.sh
# يوميًّا ٣:١٥ فجرًا:
# 15 3 * * * cd $HOME/asrab-v2 && ./deploy/backup.sh >> ~/asrab-backup.log 2>&1
```

يُبقي آخر أربعة عشر يومًا، **ويرفض نسخةً فارغة**: `pg_dump` الفاشل عبر أنبوبٍ
يُنتج ملفًّا صالح الشكل خاوي المحتوى، فتُكتشَف الكارثة يوم الاستعادة لا يوم
النسخ.

**ونسخةٌ على القرص نفسه ليست نسخةً احتياطية** — انقلها خارج الخادم.

## ٧. ما بقي بيدك وحدك

| | |
|---|---|
| حساب سحابيّ ونطاق | لا يُنشآن بالنيابة. والموصى به Oracle بمنطقة **جدّة** — تُختار **مرّةً عند التسجيل** ولا تُغيَّر بعدها، فانتبه لها |
| **نقل النسخ خارج الخادم** | مُجدوَلةٌ محليًّا، **ونسخةٌ على القرص نفسه ليست نسخةً احتياطية** — `rclone`/`scp` في `cron` |
| مراجعة أمان مستقلّة | ما في المستودع راجعَه كاتبُه وحده |
| قرار معايرة الأوزان | بعد شهر بيانات حقيقية (ف-٨) |
| حدُّ «الصندوق الأسود» | قرارُ منتجٍ معلَّق — `API.md §١` |

## ٨. إن تعثّر شيء

| العَرَض | الفحص الأوّل |
|---|---|
| الموقع لا يفتح | `docker compose -f docker-compose.prod.yml --env-file .env.prod ps` — هل `app` بحالة `healthy`؟ |
| `app` غير سليمة | `… logs --tail=80 app` · وغالبُ السبب القاعدة: `… logs --tail=40 db` |
| **الإقلاع يُرفض برسالة** | هذا الحرس يعمل كما يجب — اقرأ الرسالة، فهي تسمّي الإعداد الناقص بعينه |
| الشهادة لا تُصدَر | `… logs caddy` · وغالبًا سجلّ A لا يشير للخادم بعد، أو ٨٠ محجوب |
| `401 لا منظمة مهيّأة بعد` | لم يُشغَّل `flask bootstrap-org` — §٣ |
| القرص ممتلئ | `docker system prune -af` · وتدويرُ السجلّات مضبوطٌ أصلًا، فافحص حجم القاعدة والنسخ |
