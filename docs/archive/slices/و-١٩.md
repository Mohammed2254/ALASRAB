## الفرز

مختلفة الطبيعة عن كل شرائح `ui/` السابقة: لا شاشة ولا عقد API، **بنية
تحتية بحتة**. تُقسَّم لثلاث مراحل مستقلّة القيمة (كلٌّ ينفع بلا التالي):

**أ. تحقّق محليّ** — `docker compose up` يشغّل كامل المكدَّس (قاعدة + تطبيق
مبنيّ) على هذا الجهاز، بلا منصّة سحابية. **طُلب أوّلًا صراحةً** — "تجربة
على لوكال هوست" قبل أي قرار استضافة.

**ب. اختيار المنصّة** — بحثٌ حيّ (لا افتراضٌ من الذاكرة، الأسعار/الحدود
المجانية تتغيّر) عن منصّة مجانية أو رخيصة وسهلة، بعد تجربة فاشلة سابقة مع
Render (انتهت حصّته المجانية).

**ج. CI** — اختبارٌ آليّ عند كل دفعة. **بلا `push` فعليّ** — لا remote
للمستودع، فالملفّات تُكتب جاهزة لا تُختبَر حيًّا حتى يُربَط المستودع بمنصّة
استضافة كود (قرار المستخدم الصريح).

## ١. Recon — المرحلة أ (التحقّق المحليّ)

### ١.١ ما هو مقرَّر سلفًا في التوثيق — لا يُخترَع هنا

- **`ARCHITECTURE.md` §٨:** `Dockerfile` **واحد** · كل إعداد من البيئة ·
  **لا هجرة تلقائية عند الإقلاع** (Alembic يدويًّا) · `GET /health` يفحص
  اتصال القاعدة فعلًا (**مبنيّ سلفًا** — `app/__init__.py:51`) · سجلّات
  نصّية لـ`stdout` (لا إعداد إضافي، `gunicorn` يفعل هذا افتراضًا).
- **`vite.config.ts`'s تعليقٌ صريح من و-١٣ نفسه:** *"في الإنتاج تكون
  الواجهة والـAPI على أصل واحد"* — **يحسم معنى "Dockerfile واحد" فعليًّا**:
  Flask يخدم بناء `ui/` الساكن مباشرةً (لا Nginx ولا حاوية ثانية)، فيبقى
  أصلًا واحدًا كالتطوير (وكيل Vite يحاكي هذا محليًّا) بلا حاجة لـCORS في
  الإنتاج إطلاقًا.
- **`gunicorn` مُدرَجة أصلًا في `requirements.txt`** («خادم الإنتاج — خادم
  فلاسك التطويري غير آمن له») بلا استهلاك حتى الآن — نفس نمط الدروس
  ٣١/٣٢/٣٣ (بنية تُثبَت باستهلاكها لا ببنائها)، تُستهلَك هنا لأوّل مرّة.
- **`.env.example`** يعدّد كل متغيّرات البيئة المطلوبة فعلًا
  (`DATABASE_URL`, `SECRET_KEY`, `SESSION_COOKIE_SECURE`,
  `CORS_ALLOWED_ORIGINS`, `FLASK_APP`, `EXPOSE_API_DOCS`) — **قائمة
  موجودة سلفًا لا تُخمَّن**.
- **لا مسار Flask يخدم ملفًّا ساكنًا اليوم** (`app/__init__.py` يسجّل ثلاثة
  Blueprints فقط) — إضافة الخدمة الساكنة + رجوع SPA (أيّ مسار غير مطابَق
  يُعاد له `index.html`، ضروريّ لتصفّح History API — ADR-008 — عند تحديث
  صفحة أو رابط عميق) **تغييرٌ حقيقيّ في كود `api/`**، أوّل مسّ له منذ بدء
  شرائح `ui/`.

### ١.٢ ما هو منفصل عمدًا عن هذا — `api/docker-compose.yml` القائم

الملفّ الحاليّ (قاعدة تطوير وحدها، `asrab-v2-db`) **يبقى كما هو** — يخدم
تدفّق التطوير اليوميّ (`flask run` + `vite` منفصلَين) الذي لا تُغيّره هذه
الشريحة. الجديد هنا ملفّ **مختلف الغرض**: تشغيل المكدَّس **المبنيّ** (صورة
Docker حقيقية) على قاعدة بيانات **منفصلة** — لا تُخلَط بيانات التجربة
الإنتاجية ببيانات التطوير اليوميّة.

### نقطة تفتيش ٢ — البناء + التحقّق الحيّ (المرحلة أ)
✅ مكتملة.

**البناء:** `Dockerfile` (جذر المستودع، مرحلتان) + `.dockerignore` +
`docker-compose.yml` (جذر) + تغييرٌ حقيقيّ وحيد في `api/`:
`app/__init__.py` يكتسب `static_url_path=""` + معالج `404` يفرّق بين
`/api/*` (يبقى JSON بالشكل الموثَّق دون تغيير — **سلوكٌ موروث لا جديد**:
مسارٌ غير مطابَق كان يعيد HTML افتراضيّ من Werkzeug حتى قبل هذه الشريحة،
لأن معالج `Exception` القائم يُعيد كل `HTTPException` كما هي) وأيّ مسارٍ
آخر (`index.html` — رجوع SPA لروابط History API العميقة).

**تحقّقٌ حيّ كامل عبر `docker compose` فعليًّا لا `docker build` وحده:**

1. `docker build` نجح من أوّل محاولة — مرحلة `node` (`npm ci && npm run
   build`) ثم مرحلة `python` (`pip install` + نسخ `ui/dist/` إلى
   `app/static/`).
2. `docker compose up --build` شغّل `db`+`app` معًا، `app` انتظر
   `db` صحّيًّا فعلًا قبل الإقلاع (`depends_on: condition: service_healthy`).
3. `GET /health` أعطى `{"status":"ok"}` **قبل أي هجرة** — يفحص الاتصال لا
   وجود الجداول، مطابقًا لتصميمه.
4. `flask db upgrade` **يدويًّا** (`docker compose run --rm app`) طبّق كل
   الهجرات الأربع عشرة من الصفر بنجاح على قاعدة فارغة تمامًا.
5. `seed.py` عبر نفس آلية `run --rm` نجح، أنتج ٤ طلاب وساعاتهم.
6. طلب دخول حقيقيّ (`curl` بترويسة `Origin` صحيحة) أعاد جلسة صحيحة ٢٠٠؛
   رمزٌ خاطئ أعاد خطأ smorest المُهيْكل ٤٠١ (`{"code","message","status"}`)
   دون تغيّر.
7. أصلٌ ثابتٌ حقيقيّ (`/assets/index-*.js`) خُدم بحجمه ونوعه بالضبط
   (٣٨٥٬٠٩٠ بايت، مطابقًا لناتج `vite build`).
8. **قياسٌ بصريّ حقيقيّ عبر Playwright ضدّ الحاوية** (لا `curl` وحده): دخولٌ
   كامل، بطاقة الطيّار تُرسَم بشريط تبويب حقيقيّ، ثم **إعادة تحميل صفحة
   كاملة** (لا تنقّل SPA) على `/admin/report` مباشرةً — نجحت ورسمت الشاشة
   الصحيحة، مؤكِّدةً أن معالج الرجوع يعمل فعليًّا لا نظريًّا.

**عيبٌ حقيقيّ واحد اكتُشف بالقياس الحيّ — في إعداد الاختبار نفسه لا في
الكود:** أوّل محاولة تسجيل دخول عبر متصفّح حقيقيّ (Playwright) عبر
`http://127.0.0.1:8000` تجمّدت — `CORS_ALLOWED_ORIGINS` في
`docker-compose.yml` كان يحمل `http://localhost:8000` فقط، بينما
المتصفّح يرسل ترويسة `Origin: http://127.0.0.1:8000` **فعليًّا** لصفحة
فُتحت بذاك العنوان — و`127.0.0.1` و`localhost` أصلان مختلفان تمامًا
للمتصفّح رغم إشارتهما لنفس الجهاز (ADR-006 يفحص التطابق الحرفيّ لا
الدلاليّ). أُضيف `http://127.0.0.1:8000` إلى القائمة، وأُعيد القياس
فنجح فورًا. **لم يُكتشَف بـ`curl` الأوّل** لأنه مرّر ترويسة `Origin`
يدويًّا مطابقة للقائمة عمدًا — درسٌ في أن اختبار API بأداة سطر أوامر لا
يثبت أن متصفّحًا حقيقيًّا سينجح بنفس الشرط.

**آلة التحقّق:** `pytest` (خارج Docker، على الكود المعدَّل نفسه) →
**٣٧٠/٣٧٠ بلا تغيير** — تعديل `app/__init__.py` الوحيد لم يكسر شيئًا.
بوابة الشرائح ٢٣١/٢٣١ (صفر معيار جديد — بنية تحتية لا عقد).

## ٦. المرحلة ج — CI + طبقة HTTPS

**CI:** `.github/workflows/ci.yml` — أربع وظائف مطابقة لـ"البوابات الستّ"
(`api` عبر `pytest` بخدمة Postgres، `ui` (الأنواع + الاختبارات + بوابات
AST/لون/عقد + `oxlint` + البناء وميزانية الأداء)، انحدار `web/`، وبوابة
الشرائح). **القياس البصريّ الحيّ (Playwright) لم يُدرَج** — يحتاج `api`+`ui`
يعملان معًا، لا يناسب مصفوفة CI بسهولة؛ يبقى يدويًّا قبل إغلاق كل شريحة
كما كان طوال و-١٣..و-١٨. **لن يعمل فعليًّا حتى يُربَط المستودع بـGitHub**
(قرار المستخدم الصريح، `§الفرز`) — صحّة الصياغة تحقَّقت محليًّا (تحليل
YAML كامل + عدّ الوظائف) لا بتشغيل حقيقيّ.

**HTTPS بلا نطاق بعد:** المستخدم لا يملك نطاقًا اليوم ("لاحقًا"). القرار:
`docker-compose.prod.yml` + `deploy/Caddyfile` يدعمان **مسارين بديلين**
لا مسارًا واحدًا يفرض قرارًا الآن — `caddy` (شهادة تلقائية بمجرّد توفّر
نطاق) أو `cloudflared` (رابط `trycloudflare.com` فوريّ بلا نطاق ولا حساب،
معطَّلٌ افتراضيًّا كتعليق جاهز للتفعيل). كلاهما موثَّقٌ خطوة بخطوة في
`docs/DEPLOY.md` الجديد.

**عيبٌ حقيقيّ اكتُشف بالتحقّق الآليّ لا بالعين:** `docker compose config`
على `docker-compose.prod.yml` أوّل مرّة أعطى `mapping values are not
allowed in this context` — قيمة `SECRET_KEY` غير المقتبَسة تضمّنت نصّ
خطأ `${VAR:?...}` بفاصلتين رأسيّتين (`:`) دون تسجيل النصّ كسلسلة واحدة،
فظنّ محلّل YAML أن الثانية تبدأ مفتاحًا جديدًا. أُصلح بتسجيل كل قيم
`${VAR:?message}` كسلاسل مقتبَسة صراحةً، ثمّ **أُثبت الحارس نفسه عدائيًّا**:
تشغيل `docker compose config` بلا `DB_PASSWORD` أعطى رسالة الخطأ العربية
المكتوبة بالضبط لا عطلًا مبهمًا — يحمي من نشرٍ بأسرار ناقصة صامتة.

**عيبٌ ثانٍ — أمنيّ لا نحويّ:** `.gitignore` الجذر كان يستبعد `.env`
حرفيًّا فقط، لا `.env.prod` الذي يوثّقه `docs/DEPLOY.md` نفسه كخطوة أولى!
لو اتُّبع الدليل حرفيًّا ثم `git add .` لاحقًا، كانت أسرار الإنتاج
(كلمة مرور القاعدة، `SECRET_KEY`) لتُلحَق بالمستودع. أُصلح إلى `.env*` +
استثناء صريح لـ`api/.env.example` (الملفّ الوحيد المقصود تتبّعه)،
وتحقَّق `git check-ignore` أن كل ملفّ يُعامَل كما يجب.

**آلة التحقّق:** تحليل `ci.yml` كـYAML صالح (بايثون `yaml.safe_load`) وعدّ
الوظائف الأربع؛ `docker compose config` صالحًا لـ`docker-compose.prod.yml`

## الفحص الذاتي الإلزامي قبل `= COMPLETE`

1. كل معيار جديد له إثبات عدائي فردي كامل؟ **لا معيار جديد** — بنية
   تحتية لا عقد؛ ما وُجد بدله ثلاثة عيوب حقيقية (تطابق Origin، بناء
   YAML، فجوة `.gitignore`) اكتُشفت وأُصلحت، **الأخيران مُثبَتان بزرع
   وإسقاط فعليّ لا افتراضًا**.
2. صفر تراجع؟ **نعم** — `pytest` ٣٧٠/٣٧٠ خارج Docker، بوابة الشرائح
   ٢٣١/٢٣١، صفر مسّ لـ`ui/`.
3. الأرقام الخام مصرَّحة؟ **نعم** — كل رقم منصّة في `§٥` من بحثٍ حيّ
   بمصادره، لا من الذاكرة.
4. كل قرار Reconcile موثَّق بسببه؟ **نعم** — بما فيه قرار "مسارين
   بديلين لا مسارًا واحدًا" لطبقة HTTPS، ناتجًا مباشرًا عن عدم حسم
   المستخدم لسؤال النطاق بعد.
5. آلة التحقّق كاملةً شُغِّلت على الحالة النهائية؟ **نعم بقدر الممكن
   محليًّا** — `docker compose up` حيّ فعليّ، `CI` تحقّقًا بنيويًّا لا
   تشغيليًّا (لا remote، قرارٌ صريح لا نقص).
6. لم يُبنَ ما تقرّر تأجيله؟ **نعم** — لا `push` فعليّ، لا اختيار نهائيّ
   لمسار HTTPS (النطاق قرار المستخدم لاحقًا)، لا تشغيل فعليّ على Oracle
   أو Hetzner (يحتاج بيانات اعتماد سحابية لا أملكها ولا ينبغي أن أطلبها).

**النتيجة: و-١٩ = COMPLETE للعمل الذي يقع في هذا الجهاز.** Docker محليّ
يعمل فعليًّا ومُختبَر حيًّا بالكامل (بناء + هجرة + بذرة + دخول حقيقيّ +
قياس بصريّ بعد إعادة تحميل رابط إداريّ عميق). منصّة الاستضافة مُختارة
ببحثٍ حيّ (Oracle أوّلًا، Hetzner احتياطيًّا)، وCI جاهزٌ للعمل من أوّل
دفعة بمجرّد ربط المستودع. **الخطوة الأخيرة فعليّة لا توثيقية**: تنفيذ
`docs/DEPLOY.md` على خادم حقيقيّ — فعلٌ يحتاج حساب المستخدم السحابيّ
وقراره، لا كودًا إضافيًّا هنا.
