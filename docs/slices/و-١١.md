## ١. Recon — المقارنة الحرفية مع و-٤ القائمة

فُحص `models/reading.py` و`services/reading.py` و`DATABASE.md` §٣.١ سطرًا
سطرًا قبل أي قرار:

| البند | الحقيقة في الكود | القرار |
|---|---|---|
| الشكل | تاريخ + صفحات + كتاب + حالة + اعتماد بحدث — **مطابق حرفيًّا** | **تمديد لا جدول جديد** |
| `UNIQUE` | `(user_id, read_on, book_title)` | يُوسَّع إلى `(..., activity_type)` |
| يوم الأسبوع | **لا قيد اليوم** | قيد جديد فعليًّا، خدمة **وقاعدة معًا** (ث-١٨) |
| الوزن | `reading`=٠.١٥ مبذور | **لا يُعاد استعماله** — `tahdir` وزنٌ مستقلّ، رقمه TBD (صفٌّ لاحقًا لا هجرة) |
| `kind` على الحدث | `KIND='reading'` (`services/reading.py`) | **يبقى `'reading'` للبرنامجين معًا** — `services/readiness.py` يحسب «أرضي» من `kind IN ('quran','reading')`؛ سابقة `seed.py` الحاسمة: أنواع `activity_type` متعدّدة تحت `kind` ثابت واحد |
| الاعتماد الجماعي | `POST /admin/readings/approve` ذرّي بالكامل (ق-٢٤) | **يُعاد استعماله حرفيًّا بلا تعديل** — عامٌّ على معرّف الطلب أصلًا |
| إضافة نيابةً عن طالب | غير موجودة | مسار جديد، نفس نمط `services/quran.add_entry` (و-٦): معتمَد فورًا، ذرّيّ مع `audit_log` |

**البديل المرفوض:** جدول `tahdir_submissions` منفصل — يكرّر ~٩٠٪ من البنية
والمنطق (نفس القيود المزدوجة ث-٥/ث-٦) لاختلافٍ في السياسة فقط (يوم الأسبوع،
الحدّ الأدنى، الوزن، التقرير) — وكلّها تُحلّ بعمود وفحص خدمة وتقرير جديد لا
ببنية جديدة (`AGENTS.md`: «طبقة تُضاف حين يوجعنا غيابها»).

## ٢. Reconcile — القرارات المؤكَّدة

| # | السؤال | القرار المؤكَّد |
|---|---|---|
| ١ | الكتاب | الحقل الحرّ القائم كما هو — **لا** إعداد «كتاب حاليّ» على مستوى المنظمة. القياس بعدد الصفحات لا هوية الكتاب |
| ٢ | عتبة «متعثّر» | **أقلّ من ١٠٠٪** من ٢٨ صفحة — بلا هامش تسامح |
| ٣ | «يوم مكتمل» | **إرسال معتمَد** (لا معلَّق) بصفحات **≥٧** — مطابقًا لمبدأ FR-021 (لا استحقاق قبل الاعتماد) |
| ٤ | يوم الأسبوع | فحص **خدمة وقاعدة معًا** (دفاع مزدوج، ث-١٨) — لا واجهة وحدها |
| ٥ | عمود مُميِّز | `activity_type` نصّ مفتوح على `reading_submissions` — `'reading'` و`'tahdir'` |
| ٦ | الاعتماد الجماعي | إعادة استعمال `POST /admin/readings/approve` **حرفيًّا** — الواجهة تُمرّر كل المعرّفات المعلَّقة، صفر منطق خلفيّ جديد |
| ٧ | إضافة إدارية | مسار جديد `POST /admin/tahdir/entry`، يستدعي دالّة خدمة جديدة تُنشئ الطلب **معتمَدًا فورًا** (`ledger.append_pending` + `audit.record` + `commit` واحد) |
| ٨ | نطاق SCOPE.md | FR-090..093 نطاقٌ **جديد** يُضاف لا يُصحَّح — أُضيف بالفعل في هذه النقطة من Reconcile (checkpoint ١) |

**قرار تصميم إضافي محسوم أثناء Reconcile (امتداد سابقة لا قرار من الصفر):**
النسبة الأسبوعية `percent = pages_total / 28 × 100` (مجموع الصفحات المعتمَدة
في نافذة الأحد–الأربعاء الحالية)، **منفصلة تمامًا** عن عدّ الأيام المكتملة
(`days.completed`) — كلاهما يُعرَضان معًا لا أحدهما بديلًا. هذا تفسير مباشر
لنصّ الطلب («يبيّن أيامي المكتملة **و**نسبتي») لا قرارًا يستحقّ توقّفًا: لا
مقايضة جوهرية بديلة تُغيّر سلامة الدفتر أو معناه المالي.

**لماذا لا يوجد شرط توقّف حقيقيّ هنا:** كل قرار أعلاه امتدادٌ لسابقة قائمة
(`activity_type` المفتوح كـ`weights`، الدفاع المزدوج كـث-١٣/ث-١٧، `kind`
موحَّد كـ`seed.py`، إضافة إدارية كـ`quran.add_entry`) — لا تصميم أوّل من نوعه.

## ٣. تدفّق البيانات

```
POST /api/me/tahdir                              POST /api/admin/tahdir/entry
  └─ @login_required                                └─ @admin_required
  └─ services/reading.submit(                        └─ services/reading.admin_submit(
       org, user_id, read_on, pages,                      org, actor_id, user_id, read_on,
       book_title, activity_type="tahdir")                pages, book_title, activity_type)
       ├─ رفض تاريخ مستقبليّ                              ├─ نفس فحوص submit + يوم الأسبوع
       ├─ فحص يوم الأسبوع لو tahdir                        ├─ rules.engine.hours_for(Achievement)
       └─ INSERT pending (ث-١٨ في القاعدة أيضًا)            ├─ ledger.append_pending([EventSpec])
                                                            ├─ INSERT approved (point_event_id مملوء من البداية)
GET /api/me/tahdir                                         ├─ audit.record(kind='reading_admin_entry')
  └─ services/reading.weekly_report(org, user_id)          └─ commit واحد
       └─ نفس الدالّة يستدعيها GET /admin/tahdir/report لكل طالب
```

**كلاهما يظهر تلقائيًّا** في `GET /me/events` (`kind='reading'` القائم بلا
تعديل) — لا مسار جديد لعرض الساعات، فقط لإنشائها وللتقرير الأسبوعي.

## ٧. معايير القبول

| ق-١٥٧ | تحضير خارج الأحد–الأربعاء ⇒ رفض (خدمة **وقاعدة**، ث-١٨) | تحضير بتاريخ خميس/جمعة/سبت يُقبل |
|---|---|---|
| ق-١٥٨ | داخل النطاق بصفحات ≥٧ ⇒ يُقبل معلَّقًا؛ وقيد `UNIQUE` الموسَّع لا يعيق برنامجين مختلفين بنفس اليوم/الكتاب | برنامجان مختلفان يتصادمان خطأً |
| ق-١٥٩ | صفحات <٧ ⇒ `٤٢٢` | صفحات دون الحدّ الأدنى تُقبل |
| ق-١٦٠ | التحضير لا يمنح ساعات قبل الاعتماد | رصيد يتغيّر بمجرّد الإرسال |
| ق-١٦١ | إرسال مزدوج (نفس اليوم/الكتاب/البرنامج) ⇒ `٤٠٩` | تكرار يُقبل بصمت |
| ق-١٦٢ | اعتماد تحضير عبر `/admin/readings/approve` القائم يستعمل **وزن `tahdir` لا `reading`** | حساب الساعات بوزن القراءة العامّة خطأً |
| ق-١٦٣ | عزل القوائم الإدارية: `/admin/tahdir` تحضير فقط، `/admin/readings` قراءة فقط | برنامج يظهر مختلطًا في قائمة الآخر |
| ق-١٦٤ | عزل قوائم الطالب: `/me/tahdir` و`/me/readings` كلٌّ يرى برنامجه فقط | نفس الخلط من جهة الطالب |
| ق-١٦٥ | الإضافة الإدارية المباشرة تُنشئ حدثًا **معتمَدًا فورًا** بساعات محسوبة من المحرّك | رقمٌ يُكتب مباشرةً متجاوزًا المحرّك |
| ق-١٦٦ | الإضافة الإدارية ترفض يوم/صفحات مخالفة — **لا استثناء إداريّ** | المشرف يتجاوز قواعد اليوم/الحدّ الأدنى |
| ق-١٦٧ | الإضافة الإدارية تكتب `audit_log` منسوبًا، **ذرّيًّا مع الحدث** | إضافة بلا أثر تدقيق |
| ق-١٦٨ | غير مشرف ⇒ `403` · بلا جلسة ⇒ `401` على مسارات `/admin/tahdir/*` | طيّار يصل شاشات إدارية |
| ق-١٦٩ | «يوم مكتمل» = معتمَد بصفحات ≥٧ — **لا معلَّق** | معلَّق يُحتسَب مكتملًا خطأً |
| ق-١٧٠ | `percent = pages_total/28×100`، و`struggling = percent<100` **بلا هامش** | نسبة أو عتبة تعثّر محسوبة خطأً |
| ق-١٧١ | تقرير المنظمة **يشمل من لم يُرسل شيئًا** (٠٪ · متعثّر) | تقرير يستبعد الغائبين |
| ق-١٧٢ | **صفر تراجع**: طابور القراءة العامّ يعمل كما كان رغم برنامج تحضير جديد | إضافة تحضير تكسر و-٤ المغلقة |
| ق-١٧٣ | شاشات `Tahdir`/`TahdirQueue`/`TahdirReport` **بلا حساب أعمال** وتجتاز القياس @٣٧٥px | حساب/مقارنة في الواجهة، أو عيب بصري |
| ق-١٧٤ | إرسال مزدوج عبر الإضافة الإدارية المباشرة ⇒ `٤٠٩` **لا `٥٠٠`** | `IntegrityError` خام يتسرّب من `db.session.flush()` غير المحروس |

**ق-١٧٤ لم تكن في الخطّة الأصلية أعلاه** — اكتُشفت أثناء الإثبات العدائي
لـق-١٦٦ (انظر §سجلّ التقدّم، نقطة تفتيش ٣): `admin_submit()` كان يلتقط
`submission.id` بـ`db.session.flush()` **قبل** `try/except IntegrityError`
الذي يحرس `commit()` وحده — والإدراج الفعليّ يقع عند `flush` لا `commit`،
فيسرّب `500` خامًا عند تكرار حقيقيّ بدل `409` المقصود. أُصلحت فورًا (كلا
النداءين في حارسٍ واحد)، وأُضيف معيارٌ ثامن عشر لتوثيقها ومنع تكرارها.

### ٨.٢ الإثبات العدائي — كامل، لا عيّنة

**الجدول أدناه هو ما وقع فعليًّا في الدورة الحيّة، لا الخطّة الأصليّة كما
كُتبت قبل التنفيذ** — ثلاث مخالفات سقطت لسببٍ مختلف عمّا افتُرض ابتداءً
(ق-١٥٧، ق-١٧١)، ومخالفتان كشفتا اختبارًا ضعيفًا فأُصلح الاختبار نفسه قبل
إعادة المحاولة (ق-١٦٠، ق-١٦٦) — مفصَّلٌ كلٌّ تحت جدوله.

| المعيار | المخالفة | السقوط الفعليّ |
|---|---|---|
| ق-١٥٧ | `if False:` بدل فحص `weekday()` في `_check_tahdir_day` | `assert 409 == 422` — **لا** `201 == 422` كما افتُرض: قيد ث-١٨ في القاعدة أمسك المخالفة رغم تعطيل فحص الخدمة (الدفاع المزدوج يعمل)، لكن معالج `IntegrityError` العامّ في `submit()` حوّلها ٤٠٩ («مكرَّر») لا ٤٢٢ («يوم خاطئ») — رسالة غير دقيقة، لا ثغرة أمنية |
| ق-١٥٨ | استبعاد الاثنين من `TAHDIR_ALLOWED_WEEKDAYS` | `assert 422 == 201` ليوم اثنين صالح |
| ق-١٥٩ | `Range(min=1)` بدل `min=7` في `SubmitTahdirSchema` | `assert 201 == 422` لـ٦ صفحات |
| ق-١٦٠ | `status="approved"` مباشرةً في `submit()` | **الاختبار الأصليّ لم يفشل** — لم يكن يتحقّق من `r.status_code`، فمرّ صامتًا حين رفض ث-٥ الإدراج (صفرُ صفوف يجعل تأكيدَي الرصيد/`point_event_id` صحيحين تفاهةً). أُضيف `assert r.status_code == 201` أوّلًا، فسقطت المخالفة بـ`assert 409 == 201` |
| ق-١٦١ | حذف `except IntegrityError` من `submit()` | `500` خام (`UniqueViolation` غير مُلتقَط) بدل `409` مضبوط |
| ق-١٦٢ | إعادة `activity_type=ACTIVITY` (الثابت) في `approve()` بدل `s.activity_type` | `assert '1.50' == '20.00'` — وزن `reading` (٠.١٥) بدل `tahdir` (٢.٠٠) |
| ق-١٦٣ | حذف شرط `activity_type` من `pending_queue()` | تحضير يظهر في `/admin/readings` والعكس |
| ق-١٦٤ | حذف شرط `activity_type` من `list_for_user()` | نفس الخلط من `/me/*` |
| ق-١٦٥ | `hours = Decimal(pages)` بدل `hours_for(...)` في `admin_submit()` | `assert '10.00' == '30.00'` |
| ق-١٦٦ | حذف نداء `_check_tahdir_day` من `admin_submit()` | **الاختبار الأصليّ لم يفشل للسبب المُدَّعى** — لا وزن `tahdir` مزروعًا في ثابتة الاختبار، فـ`hours_for()` رفضت بـ٤٢٢ **قبل** الوصول إلى فحص اليوم أصلًا؛ نجاحٌ صدفويّ لا إثباتًا. أُضيف `_add_tahdir_weight` + تأكيد نصّ الرسالة، فسقطت المخالفة بـ`assert 500 == 422` (اكتشفت أيضًا ق-١٧٤ أدناه) |
| ق-١٦٧ | حذف نداء `audit.record` من `admin_submit()` | `AttributeError: 'NoneType' object has no attribute 'kind'` |
| ق-١٦٨ | `@login_required` بدل `@admin_required` على `TahdirQueue` | `assert 200 == 403` |
| ق-١٦٩ | حذف `status == "approved"` من فلتر `_tahdir_rows_this_week` | `assert True is False` — معلَّق يُحتسَب مكتملًا |
| ق-١٧٠ | تبديل `TAHDIR_WEEK_TARGET_PAGES` إلى ١٠٠ في `_summarize_week` | `assert 10.0 == 35.7` |
| ق-١٧١ | بناء تقرير المنظمة من `rows` وحدها بلا دمج القائمة الكاملة | `assert 1 in set()` — **كلا الطالبين** اختفى (لا واحد فقط كما افتُرض): لا أحد أرسل شيئًا هذا الأسبوع الحقيقيّ وقت الاختبار، فـ`rows` فارغة تمامًا بلا الجذر (`roster`) |
| ق-١٧٢ | نفس مخالفة ق-١٦٣ (الفلتر المشترَك) — دليلٌ من الاتجاه الآخر | `assert 2 == 1` — تحضيرٌ يظهر في `/admin/readings` |
| ق-١٧٣أ (بلا قاعدة عمل) | `week.pages_total / week.target_pages > 0.6` بدل `week.struggling` في `Tahdir.jsx` | `check:arch` ⇒ `❌ مقارنات (>) · عمليات حسابية (/) · أرقام مجال (0.6)` |
| ق-١٧٣ب (قياس بصري) | زرّ «رجوع» إلى `min-h-[28px]` في `TahdirQueue.jsx` | `visual-qa.mjs` ⇒ `❌ ق-١٤: … 44×28 < 44` |
| ق-١٧٤ | فكّ حراسة `db.session.flush()` عن `try/except IntegrityError` في `admin_submit()` (استعادة الشكل الأصليّ قبل الإصلاح) | `IntegrityError` (`UniqueViolation`) خام يتسرّب — `500` بدل `409` |

**كل مخالفة أُعيدت فور تأكيد السقوط** (بالمقارنة بايتًا ببايت مع نسخة
محفوظة قبل الزرع)، وأُعيد تشغيل الاختبار المحدَّد فالسويت الكامل في
